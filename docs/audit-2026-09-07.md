## 3. Constats P1 — détail

### D-01 — « Annuler » d’un toast : l’échec de la restauration est totalement muet (les 8 chemins d’undo)

- **Où** : app/js/ui.js — 177
- **Vérification** : reproduit
- **Constat** : Le bouton d’action du toast ferme le toast PUIS exécute l’action sans aucun try/catch : `btn.addEventListener('click', async () => { fermer(); await action(); })`. Toutes les actions d’annulation appellent `restaurer(objets)` (eleves.js:199 et :487, sequences.js:186 et :211, notes.js:337, inaptitudes.js:358, documents.js:136, observations.js:31, edt.js:126). Si `restaurer` rejette (quota plein au moment de ré-écrire les blobs d’un élève — photo + certificat ≈ 600 Ko —, base fermée par `onversionchange`, disque), la promesse est rejetée sans gestionnaire : le toast a déjà disparu, aucun message, et dans plusieurs cas la navigation prévue après (`location.hash = …`) n’a pas lieu, ou bien un `rafraichir()` n’est jamais appelé.
- **Preuve** : ui.js:177 `btn.addEventListener('click', async () => { fermer(); await action(); });` — eleves.js:487 `toast(\`${eleve.prenom} ${eleve.nom} supprimé\`, { action: async () => { await restaurer(objets); location.hash = … } })` — aucun catch dans aucune des 9 actions.
- **Scénario** : Android presque plein. Le prof supprime par erreur un élève avec photo et certificat (la suppression, elle, réussit : elle libère de la place). Il clique « Annuler » dans les 8 s. `restaurer` doit ré-écrire ~600 Ko de blobs + les enregistrements → QuotaExceededError à la validation → rejet. Le toast est déjà fermé, rien ne s’affiche, la vue reste sur la classe : l’élève et tout son historique restent supprimés alors que le prof est certain d’avoir annulé.
- **Impact** : Le seul filet de récupération de l’app peut échouer sans le dire ; perte d’historique élève (appels, notes, certificats) crue récupérée. Réparation impossible sans sauvegarde antérieure.
- **Correction minimale** : Dans ui.js:177 : `btn.addEventListener('click', async () => { fermer(); try { await action(); } catch (e) { toast(\`Annulation impossible : ${e?.message \|\| e}\`, { duree: 12000 }); } });`. Une ligne, couvre les 9 chemins.

### A01 — Origine partagée : IndexedDB et localStorage sont lisibles par les autres PWA de alemoine4.github.io, et le guide affirme le contraire

- **Où** : app/js/io.js + app/js/state.js + docs/guide-installation.md + docs/modele-donnees.md — io.js:5 ; state.js:7 ; guide-installation.md:50 ; modele-donnees.md:113
- **Vérification** : factuel (plateforme) — structurant
- **Constat** : IndexedDB, localStorage et Cache Storage sont cloisonnés PAR ORIGINE, jamais par chemin. https://alemoine4.github.io/carnet-eps/ partage son origine avec les autres PWA publiées sur ce compte GitHub Pages (Le Bar Clandestin, dont docs/test-terrain.md prévoit l'installation sur le même appareil). Tout script chargé sous cette origine peut faire indexedDB.open('carnet-eps') et lire les 14 stores. Le projet a identifié le problème pour les caches (H05, commentaire service-worker.js:47) mais jamais pour les données ; la ligne « Limites » du registre RGPD ne mentionne que l'absence de chiffrement.
- **Preuve** : io.js:5 `const DB_NOM = 'carnet-eps';` (nom fixe, aucune isolation possible) ; state.js:7 `const CLE_PREFS = 'carnet-eps:prefs';` ; index.html:8 `script-src 'self'` — « self » = l'origine entière, donc la CSP ne compartimente rien. docs/guide-installation.md:50 : « Personne d'autre n'y a accès tant que l'appareil est verrouillé ». docs/modele-donnees.md:113 : « Limites \| Pas de chiffrement fort sans clé utilisateur » — rien sur l'origine partagée. service-worker.js:47-48 reconnaît pourtant explicitement « alemoine4.github.io héberge d'autres PWA ».
- **Scénario** : Le prof installe Le Bar Clandestin (même origine) sur son téléphone. Une page de cette app est un jour compromise, ou l'utilisateur y colle un bout de code trouvé en ligne : trois lignes suffisent pour exporter l'intégralité du carnet EPS. Aucune interaction avec Carnet EPS n'est nécessaire, et rien dans l'app ne le signalerait.
- **Impact** : La garantie de confidentialité annoncée à l'utilisateur est fausse : la frontière de sécurité réelle n'est pas « l'appareil verrouillé » mais « toutes les applications publiées sur ce compte GitHub ». Les données concernées relèvent de l'article 9 RGPD (santé : notesPerso PAI/asthme, photos de certificats) et concernent des mineurs.
- **Correction minimale** : (1) Indispensable et sans code : reformuler docs/guide-installation.md:50 et ajouter la limite à la ligne « Limites » du registre RGPD (docs/modele-donnees.md:113). (2) De fond, à décider par un AVIS : publier Carnet EPS sur une origine propre (dépôt dédié servi sous son propre sous-domaine), ce qui isole IndexedDB, localStorage et Cache Storage sans toucher une ligne de code applicatif — au prix d'une migration export → import des données existantes. *(structurant : avis préalable)*

### A02 — EDT : ouvrir puis enregistrer un créneau dont la classe est archivée écrase classeId par une chaîne vide

- **Où** : app/js/modules/edt.js — 20, 49, 86, 104, 113
- **Vérification** : reproduit
- **Constat** : vueEDT ne charge que les classes NON archivées (ligne 20) et construit selClasse à partir de cette seule liste (ligne 49). ouvrirForm fait `selClasse.value = creneau?.classeId \|\| classes[0].id` (ligne 86) : si le créneau pointe vers une classe archivée, aucune <option> ne correspond, le navigateur met selectedIndex = -1 et select.value devient ''. btnEnregistrer relit `classeId: selClasse.value` (ligne 104) sans aucun contrôle — seules les heures sont validées (94-98) — et écrit le créneau (113). Rien n'interdit d'archiver une classe qui a des créneaux : le garde-fou B22 (eleves.js:188) ne protège que la SUPPRESSION, pas l'archivage (eleves.js:177-181 bascule `archivee` sans rien vérifier).
- **Preuve** : edt.js:20 `const classes = (await tous('classes')).filter((cl) => !cl.archivee).sort(trierClasses);` · edt.js:86 `selClasse.value = creneau?.classeId \|\| classes[0].id;` · edt.js:104 `classeId: selClasse.value,` · edt.js:113 `await enregistrer('edt', rec);` (aucune validation de classeId) · edt.js:150 `el('span', { class: 'edt-classe' }, classe?.nom \|\| 'Classe ?')` — la ligne affiche déjà « Classe ? », ce qui invite justement à cliquer dessus pour corriger.
- **Scénario** : Le prof archive la 3B en janvier. Le créneau EDT du mardi 10h reste et s'affiche « Classe ? ». Il clique dessus pour corriger l'installation ou l'horaire, puis « Enregistrer ». Le créneau est réécrit avec classeId: ''.
- **Impact** : Corruption silencieuse et définitive du lien créneau → classe : l'accueil fera `lire('classes','')` → « Classe ? » puis « Aucune séquence en cours », et la classe d'origine étant archivée elle n'est même plus proposée dans la liste pour réparer. Aucun message.
- **Correction minimale** : Refuser l'enregistrement si `!selClasse.value` (même traitement que les heures invalides, edt.js:94-98) et ajouter la classe du créneau en cours d'édition aux options même si elle est archivée (concaténer `classes` avec la classe de `enEdition` quand elle en est absente).

### B01 — Grille d'appel : l'anneau de focus clavier est rogné par overflow:hidden, invisible partout

- **Où** : app/css/components.css — 479-488 (+ base.css:172-175 ; appel.js:311-324, 358-362)
- **Vérification** : reproduit + capture
- **Constat** : `.btn-eleve` porte `overflow: hidden`. Ses deux enfants focalisables — `.eleve-cycle` (flex:1, align-items:stretch, donc sa border-box coïncide avec les bords intérieurs de la carte, le parent n'ayant aucun padding) et `.eleve-menu` (flex:0 0 44px) — reçoivent l'unique règle de focus du projet, `outline: 3px solid var(--c-accent); outline-offset: 2px`. Un outline est peint HORS de la border-box ; à +2 px il tombe hors de la padding-box de `.btn-eleve`, c'est-à-dire hors de la zone de rognage. L'anneau n'est donc jamais peint (seul survit le mince segment vertical entre les deux enfants). Aucune surcharge de focus n'existe pour ces deux sélecteurs (grep `focus-visible` sur app/css : 3 occurrences, base.css:172, 180, 181).
- **Preuve** : components.css:479-488 `.btn-eleve { position: relative; display: flex; align-items: stretch; min-height: 64px; border: 2px solid var(--c-bordure); border-radius: 12px; background: var(--c-surface); overflow: hidden; }` — components.css:491-510 `.eleve-cycle { position: relative; flex: 1; min-width: 0; ... padding: 10px 12px; ... }` — base.css:172-175 `:focus-visible { outline: 3px solid var(--c-accent); outline-offset: 2px; }`. Le chemin clavier est pourtant explicite : appel.js:358-362 `cycle.addEventListener('keydown', (e) => { ... const st = RACCOURCIS_STATUT[e.key.toLowerCase()]; if (st) { e.preventDefault(); longPress = false; definirStatut(eleve, st); } });`
- **Scénario** : Appel d'une 3e de 28 élèves au clavier sur le PC de la salle des profs. Le prof tabule dans la grille : aucune carte ne change d'aspect (la seule bordure qui bouge est celle du statut, pilotée par [data-statut]). Il tape « A » en croyant être sur DUPONT alors que le focus est sur DURAND : DURAND est marqué absent, DUPONT reste présent, et rien ne le signale.
- **Impact** : Sur l'écran le plus utilisé de l'app et le seul doté d'un workflow clavier documenté, l'utilisateur ne sait jamais où il est : statut posé sur le mauvais élève, absence fausse remontée au récap trimestriel. Échec WCAG 2.4.7 Focus Visible (niveau A).
- **Correction minimale** : Une règle dans components.css, sans toucher à `overflow: hidden` (qui contient le fond de `.eleve-menu:active` dans le rayon de 12 px) : `.eleve-cycle:focus-visible, .eleve-menu:focus-visible { outline-offset: -3px; }` — l'anneau devient intérieur, donc dans la zone de rognage.

### B02 — « Terminer l'appel » sur une séance passée enregistre « présent » pour les élèves sous certificat

- **Où** : app/js/modules/appel.js — 378-382 (à comparer à 143-157)
- **Vérification** : reproduit
- **Constat** : Le pré-remplissage « inapte » est volontairement limité à la séance du jour (A14) : `if (estSeanceDuJour) { ... }` (appel.js:146). Mais le handler de « Terminer l'appel » écrit `present` pour tout élève sans enregistrement, sans jamais consulter `inaptesSet` — pourtant calculé À LA DATE DE LA SÉANCE juste au-dessus (appel.js:144-145) et déjà utilisé pour afficher la pastille 🩺 sur la carte (appel.js:318). Le geste « je complète l'appel d'hier » produit donc l'inverse exact du geste « je fais l'appel à chaud ».
- **Preuve** : appel.js:144-145 `const actives = await inaptitudesActives(seance.date); const inaptesSet = new Set(actives.map((i) => i.eleveId));` — appel.js:378-382 `btnTerminer.addEventListener('click', async () => { for (const eleve of eleves) { if (!enregs.has(eleve.id)) await definirStatut(eleve, 'present'); } });` — aucune mention de `inaptesSet` dans ce bloc.
- **Scénario** : Cours du jeudi, appel noté le vendredi matin en salle des profs (usage documenté). Le prof ouvre la séance (l'en-tête affiche bien « ⚠ séance passée »), tape ses 3 absents, puis « Terminer l'appel · 25 passés en présent ». Les 2 élèves sous certificat en cours, affichés avec la pastille 🩺 sous ses yeux, sont enregistrés « Présent ».
- **Impact** : L'inapte est compté pratiquant dans les compteurs, dans le récapitulatif trimestriel imprimé pour le conseil de classe et dans le CSV remis à la vie scolaire ; la trace de son inaptitude disparaît de l'historique d'appel. Le prof n'a aucun moyen de s'en apercevoir : la pastille 🩺 reste affichée à côté de la pastille « P ».
- **Correction minimale** : Une ligne, appel.js:380 : `if (!enregs.has(eleve.id)) await definirStatut(eleve, inaptesSet.has(eleve.id) ? 'inapte' : 'present');` — même règle que le pré-remplissage, sans écrire quoi que ce soit tant que le bouton n'est pas activé.

### B03 — Ajouter une photo d'élève et remplacer un certificat : commandes inatteignables au clavier (<label> non focalisable)

- **Où** : app/js/modules/eleves.js — 300 et 316 ; app/js/modules/inaptitudes.js:286 et 333
- **Vérification** : reproduit
- **Constat** : Deux commandes sont construites comme `<label class="btn">Texte<input type="file" hidden></label>`. Un `<label>` n'entre jamais dans l'ordre de tabulation, et l'input porte `hidden` (renforcé par components.css:741 `.btn input[type="file"][hidden] { display: none; }`), donc il n'est pas focalisable non plus. Aucun autre chemin vers ces fonctions n'existe dans l'écran. Le clic souris/tactile marche (association implicite), ce qui masque le défaut à tout test non clavier. Le même besoin est traité correctement ailleurs : inaptitudes.js:176 utilise un `<input type="file">` VISIBLE placé dans `champ('in-fichier', …)`.
- **Preuve** : eleves.js:300 `const inpPhoto = el('input', { type: 'file', accept: 'image/*', hidden: true });` — eleves.js:316 `const rangPhoto = el('div', { class: 'rang-btn' }, el('label', { class: 'btn' }, photoOK ? 'Changer la photo' : 'Ajouter une photo', inpPhoto));` — inaptitudes.js:286 `const inpRemplace = el('input', { type: 'file', accept: 'image/*,.pdf,application/pdf', hidden: true });` — inaptitudes.js:333 `const labelAjout = el('label', { class: 'btn' }, inapt.certificatId ? 'Remplacer la pièce' : 'Ajouter une photo / un PDF', inpRemplace);`. À côté, eleves.js:318 « Retirer la photo » est un vrai `<button>` : au clavier on peut retirer une photo mais pas en ajouter.
- **Scénario** : Un prof sur PC au clavier (poignet immobilisé, ou lecteur d'écran) reçoit un nouveau certificat pour un élève déjà inapte. Il ouvre Suivi → Inaptitudes → l'élève, tabule dans toute la carte « Certificat / pièce jointe » : il atteint le bouton « Ouvrir certificat.pdf », jamais « Remplacer la pièce ». Aucune touche ne l'active. Même impasse sur la fiche élève pour la photo.
- **Impact** : Deux fonctions métier — dont le remplacement d'un certificat médical, geste de terrain récurrent — sont impossibles à exécuter au clavier et invisibles pour un lecteur d'écran. Échec WCAG 2.1.1 Clavier (niveau A). B09 (audit du 05/09) avait corrigé exactement ce type de défaut sur la vignette, mais pas sur ces deux déclencheurs.
- **Correction minimale** : Remplacer chaque `<label class="btn">` par un vrai bouton qui relaie le clic : `const btnAjout = el('button', { class: 'btn', type: 'button' }, libelle); btnAjout.addEventListener('click', () => inpPhoto.click());`, l'input `hidden` restant à côté dans le même rang. Deux emplacements (eleves.js:316, inaptitudes.js:333).

### B04 — « + Nouvelle inaptitude » depuis la fiche d'un élève « parti » pré-remplit le formulaire sur un AUTRE élève

- **Où** : app/js/modules/inaptitudes.js — 127-147 (+ app/js/modules/eleves.js:436)
- **Vérification** : reproduit
- **Constat** : `vueNouvelle` ne charge que les élèves actifs et les classes non archivées, puis cherche l'élève passé en paramètre d'URL DANS cette liste filtrée. Si l'élève est marqué « parti » (`actif: false`), `initial` vaut `null` et le formulaire retombe silencieusement sur `classes[0]` et le premier élève de cette classe. Or la fiche d'un élève parti affiche quand même le bouton « + Nouvelle inaptitude » (eleves.js:436, ajouté sans condition), et rien dans le formulaire ne rappelle de quel élève on venait — il est identique à celui atteint depuis le menu général.
- **Preuve** : inaptitudes.js:127-128 `const classes = (await tous('classes')).filter((cl) => !cl.archivee).sort(trierClasses); const eleves = (await tous('eleves')).filter((e) => e.actif !== false);` — inaptitudes.js:133 `const initial = eleveIdInitial ? eleves.find((e) => e.id === eleveIdInitial) : null;` — inaptitudes.js:145-147 `selClasse.value = initial ? initial.classeId : classes[0].id; majEleves(); if (initial) selEleve.value = initial.id;` — eleves.js:436 `carteIn.append(el('div', { class: 'rang-btn' }, el('a', { class: 'btn', href: `#/inaptitudes/nouvelle/${id}` }, '+ Nouvelle inaptitude')));`
- **Scénario** : Léa a quitté l'établissement en janvier ; le prof a suivi la consigne de l'écran Aide (« sa fiche → Dans la classe : Parti »). En mars l'infirmerie transmet un certificat rétroactif la concernant. Il ouvre la fiche de Léa → « + Nouvelle inaptitude » : le formulaire s'ouvre sur « 3B / ABADIE Tom ». Il saisit dates, restrictions et photo du certificat, enregistre. Variante voisine : l'élève est actif mais sa classe a été archivée → `selClasse.value` tombe à '' (aucune option correspondante), la liste d'élèves est vide et le bouton répond « Choisissez un élève » alors qu'un élève est bien désigné dans l'URL.
- **Impact** : Une inaptitude et son certificat médical sont enregistrés sur le mauvais élève, sans le moindre signal. Cet élève sera pré-rempli « inapte » d'office à chaque appel du jour pendant toute la période (appel.js:146-156) et apparaîtra dans les alertes J-7, tandis que le vrai dossier reste vide. La correction manuelle est difficile : rien dans l'écran ne dit d'où vient l'erreur.
- **Correction minimale** : Dans `vueNouvelle`, inclure l'élève désigné même inactif — `const eleves = (await tous('eleves')).filter((e) => e.actif !== false \|\| e.id === eleveIdInitial);` — et refuser le repli muet : si `eleveIdInitial && !initial`, afficher une carte « Élève introuvable » et sortir au lieu de pré-sélectionner `classes[0]`. Symétriquement, ne pas filtrer `archivee` quand l'élève initial appartient à une classe archivée.

### C01 — Pré-remplissage de l'appel : toute inaptitude active devient « Inapte (certificat) », non pratiquant

- **Où** : app/js/modules/appel.js — 143-156 (statut posé l.151 ; libellé metier.js:13 ; formulaire inaptitudes.js:150-153 et ORIGINES l.153)
- **Vérification** : démontré par lecture
- **Constat** : Pour la séance du jour, chaque élève ayant une inaptitude active est posé d'office au statut `inapte`. `inaptitudesActives()` (metier.js:146-150) ne filtre ni sur `type` (totale/partielle) ni sur `origine` (certificat/mot/infirmerie).
